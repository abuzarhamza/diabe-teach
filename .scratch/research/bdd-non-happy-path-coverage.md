Sections 1–2 are primary-source inventories and matrices; Section 3 evaluates and prioritizes coverage gaps between the BDD HTTP suite (`tests/integration/features/`) and the in-process Vitest handler suite (`tests/functions/`); Section 4 proposes an actionable set of new BDD scenarios.

## Executive Summary

1. **Current BDD footprint:** Across the 5 Cucumber `.feature` files (`tests/integration/features/*.feature`), there are **43 scenarios** in total. **26 scenarios** exercise non-happy-path error responses (or mix a refusal into a multi-step lifecycle scenario), asserting **28 HTTP 4xx error responses** across **13 distinct `ApiErrorCode` values** (`INVALID_REQUEST_BODY`, `UNAUTHORIZED_TOKEN`, `INVALID_CREDENTIALS`, `FORBIDDEN_ROLE`, `PACK_IS_SYSTEM_PACK`, `PARTICIPANT_HAS_LEFT`, `PACK_NOT_FOUND`, `SESSION_NOT_FOUND`, `ROOM_CODE_NOT_FOUND`, `PHASE_CLOSED_FOR_SUBMISSIONS`, `ASSESSMENT_ALREADY_SUBMITTED`, `SURVEY_ALREADY_SUBMITTED`, `PACK_ALREADY_ARCHIVED`, `PACK_NOT_ARCHIVED`, `SESSION_ALREADY_COMPLETED`, `PHASE_HAS_NO_TIMER`, `CHAIN_TOPOLOGY_INVALID`).
2. **Route coverage in BDD:** The API exposes **20 `/api/v1/*` route functions** plus `GET /api/health` (`netlify/functions/*.ts`). BDD exercises **17 of the 20 `/api/v1/*` routes** in at least one scenario, and tests non-happy-path error responses on **13 of the 20 routes**. Three `/api/v1/*` routes have **zero BDD coverage** (happy or non-happy):
   - `GET /api/v1/accounts/me` (`netlify/functions/get-current-account.ts:1-15`)
   - `POST /api/v1/packs/validate` (`netlify/functions/validate-pack.ts:1-15`)
   - `POST /api/v1/sessions/:sessionId/rounds/:roundNumber/chains/:chainId/adjudicate` (`netlify/functions/adjudicate-chain.ts:1-15` — helper steps exist in `tests/integration/step-definitions/chain-submission.steps.ts:197-240`, but no `.feature` file invokes them).
3. **`ApiErrorCode` & HTTP status gaps in BDD:** Of the **29 `ApiErrorCode` values** in `docs/api/openapi.yaml:1392-1424`, **17 are covered in BDD** and **12 are never asserted in BDD**:
   - Covered in Vitest handler tests (`tests/functions/*.test.ts`), missing from BDD: `EMAIL_ALREADY_REGISTERED` (409), `ACCOUNT_TEMPORARILY_LOCKED` (423), `PACK_ALREADY_EXISTS` (409), `PACK_VALIDATION_FAILED` (422), `INVALID_PHASE_TRANSITION` (409), `CHAIN_ALREADY_SUBMITTED` (409), `CHAIN_NOT_FOUND` (404), `ADJUDICATION_LOCKED_BY_INSTRUCTOR` (409), `ASSESSMENT_INCOMPLETE` (422), `PAYLOAD_TOO_LARGE` (413), `CONCURRENT_UPDATE_CONFLICT` (409), `INTERNAL_ERROR` (500).
   - Two additional domain error classes exist in `src/domain/errors/domain-errors.ts:305-325` and `src/adapters/inbound/http/middy/domain-error.middleware.ts:123-124` (`SURVEY_COMMENTS_TOO_LONG` 422 and `INVALID_SURVEY_RESPONSE` 422), tested in `tests/functions/submit-survey.test.ts:317-351`, though not listed in the `ApiErrorCode` enum in `docs/api/openapi.yaml:1392-1424`.
   - HTTP `413 Payload Too Large` and `423 Locked` have **zero BDD scenarios**; HTTP `405 Method Not Allowed` is handled by the Netlify Functions v2 runtime (`config.method`) and is not documented in `openapi.yaml` nor tested in BDD.
4. **Where BDD adds unique value vs. Vitest handler tests:** Because BDD runs against a live `netlify dev` process over HTTP (`tests/integration/support/http-client.ts:1-306`) while Vitest handler tests invoke `create*Handler` in-process with `FakeClock` and in-memory doubles (`.scratch/session-phase-deadlines/wiki/decision-test-seam-handlers-plus-clock.md:1-14`), BDD is uniquely suited for:
   - Live Netlify v2 URL routing & `path-to-regexp` parameter extraction, including `netlify dev`'s `.html` retry quirk on 403/404 (`src/adapters/inbound/http/lambda-to-v2-wrapper.ts:9-81`).
   - Full Middy middleware ordering over real HTTP (`authMiddleware` → `requestSizeLimitMiddleware` → `jsonObjectBodyMiddleware` → `requestBodySchemaMiddleware` → handler → `domainErrorMiddleware`, `src/adapters/inbound/http/middy/api-handler.ts:35-47`).
   - Cross-kind JWT refusals (`AccountAuth` vs. `BearerAuth`, `src/adapters/inbound/http/middy/auth.middleware.ts:188-209`) with real HMAC secrets and HTTP `Authorization` headers.
   - Multi-step stateful session journeys backed by MongoDB (e.g., `PARTICIPANT_HAS_LEFT` across vote/assessment/survey routes, adjudication lock conflicts, duplicate/reversed chains).
   Conversely, exact clock-boundary tests (5s grace window, 15m account lock expiry, 12h token expiry) and deterministic write-conflict retry races (`CONCURRENT_UPDATE_CONFLICT`) should stay in `tests/functions/*.test.ts`.

## 2. Route-by-Route & Error-Code Coverage Matrix

### 2.1 Architecture Note: Route File Count & Shared Middy Pipeline

- At the top level of `netlify/functions/`, there are **20 API v1 route entrypoints** (`netlify/functions/*.ts`, each exporting `config = { path, method }` and `wrapLambdaHandler(lambdaHandler, config, AppRuntime.invocationOptions)`) plus `netlify/functions/health.ts` (`GET /api/health`), and **19 implementation modules** in `netlify/functions/{accounts,packs,sessions}/` (`list-packs.ts` exists both at top level `netlify/functions/list-packs.ts:1-47` and in `netlify/functions/packs/list-packs.ts:1-47`). Note that `docs/api/openapi.yaml:636-658` also documents a 21st operation `GET /api/v1/sessions/{sessionId}/stream` (`streamGameSessionEvents`) marked `x-implemented: false`.
- Every `/api/v1/*` route uses `createApiHandler` (`src/adapters/inbound/http/middy/api-handler.ts:35-47`), which runs:
  1. `authMiddleware` (`src/adapters/inbound/http/middy/auth.middleware.ts:125-222`) → `401 UNAUTHORIZED_TOKEN`
  2. `requestSizeLimitMiddleware` (`src/adapters/inbound/http/middy/request-size-limit.middleware.ts:22-35`) → `413 PAYLOAD_TOO_LARGE` (> 262,144 bytes)
  3. `jsonObjectBodyMiddleware` (`src/adapters/inbound/http/middy/json-object-body.middleware.ts:22-50`) → `400 INVALID_REQUEST_BODY`
  4. `requestBodySchemaMiddleware` (`src/adapters/inbound/http/middy/request-body-schema.middleware.ts:224-247`) → `400 INVALID_REQUEST_BODY` (`details: { field, reason }`)
  5. `domainErrorMiddleware` (`src/adapters/inbound/http/middy/domain-error.middleware.ts:55-150`) → maps 38 `DomainError` subclasses to `400`, `401`, `403`, `404`, `409`, `413`, `422`, `423`
  6. `unexpectedErrorMiddleware` (`src/adapters/inbound/http/middy/unexpected-error.middleware.ts:20-37`) → `500 INTERNAL_ERROR`

## 3. Prioritized Gaps in BDD Non-Happy-Path Coverage

### 3.1 High-Value BDD Gaps (Where Live HTTP, Netlify Routing, Middleware Order, or Multi-Step State Matter)

1. **Adjudication Journey & `409 ADJUDICATION_LOCKED_BY_INSTRUCTOR` / `403 FORBIDDEN_ROLE` / `404 CHAIN_NOT_FOUND` (Priority 1 — Critical Gap):**
   - `POST /api/v1/sessions/:sessionId/rounds/:roundNumber/chains/:chainId/adjudicate` (`netlify/functions/adjudicate-chain.ts:1-15`) has **3 path parameters** (`:sessionId`, `:roundNumber`, `:chainId`) extracted by `resolvePathParameters` (`src/adapters/inbound/http/lambda-to-v2-wrapper.ts:63-81`), a discriminator-based OpenAPI request schema (`AdjudicateChainRequest` in `docs/api/openapi.yaml:2244-2257`), and multi-step state transitions.
   - **Zero `.feature` scenarios** call this route, even though `tests/integration/step-definitions/chain-submission.steps.ts:197-240` already defines step helpers for peer approval and instructor final ruling!
   - Even more importantly, `409 ADJUDICATION_LOCKED_BY_INSTRUCTOR` (`AdjudicationLockedError`, `src/domain/errors/domain-errors.ts:179-188`) is **not tested in `tests/functions/adjudicate-chain.test.ts` either**—it is only tested at the domain/use-case unit level. Testing a full peer vote → instructor final ruling (`isLocked: true`) → subsequent peer vote or instructor ruling refused with `409 ADJUDICATION_LOCKED_BY_INSTRUCTOR` (plus `403 FORBIDDEN_ROLE` when a learner tries `instructor-approve` and `404 CHAIN_NOT_FOUND` for a missing `:chainId` through `netlify dev`'s 404 `.html` retry) is the single highest-value BDD addition.

2. **Cross-Kind Bearer Token Refusals Over HTTP (`AccountAuth` vs `BearerAuth`, ADR-0007) (Priority 1):**
   - The API enforces strict separation between `AccountAuth` (`kind: "account"`) and `BearerAuth` (`kind: "capability"`) in `src/adapters/inbound/http/middy/auth.middleware.ts:188-209`.
   - Currently, BDD only tests *unauthenticated* requests (no `Authorization` header) on `POST /api/v1/sessions` and `POST /api/v1/packs` (`teacher-account-journey.feature:39-43, 62-66`).
   - BDD never verifies over live HTTP that:
     - Sending an instructor's session **Capability Token** to an `AccountAuth` route (`GET /api/v1/accounts/me`, `POST /api/v1/packs`, `POST /api/v1/packs/validate`, `POST /api/v1/packs/:packId/archive`) is refused with `401 UNAUTHORIZED_TOKEN`.
     - Sending a teacher's **Account Token** to a `BearerAuth` session route (`GET /api/v1/sessions/:sessionId/rounds/1/chains` or `POST /api/v1/sessions/:sessionId/phase`) is refused with `401 UNAUTHORIZED_TOKEN`.

3. **Unexercised Account & Pack Routes (`GET /api/v1/accounts/me`, `POST /api/v1/packs/validate`) and Teacher Account / Pack Conflict Edges (Priority 2):**
   - `GET /api/v1/accounts/me` (`netlify/functions/get-current-account.ts:1-15`) and `POST /api/v1/packs/validate` (`netlify/functions/validate-pack.ts:1-15`) have no BDD scenarios at all.
   - `teacher-account-journey.feature` does not test:
     - `409 EMAIL_ALREADY_REGISTERED` when signing up with an already-registered email (including case/whitespace normalization).
     - `423 ACCOUNT_TEMPORARILY_LOCKED` on the 5th consecutive wrong password and while locked even with the correct password (requires 5 sequential HTTP calls, zero wall-clock wait).
     - `400 INVALID_REQUEST_BODY` on sign-up with an invalid email or a password under 10 characters.
     - `409 PACK_ALREADY_EXISTS` when registering the same `id` and `version` twice, and `403 PACK_IS_SYSTEM_PACK` when attempting to register a new version of `"diabe-teach"`.
     - `422 PACK_VALIDATION_FAILED` on `POST /api/v1/packs` (and `200 { valid: false }` on `POST /api/v1/packs/validate`) for a schema-valid pack that has fewer Keyword Cards than `rows × cols` (`INSUFFICIENT_CARDS`).

4. **Concept Chain Submission Refusals (`409 CHAIN_ALREADY_SUBMITTED` & `422 CHAIN_TOPOLOGY_INVALID` for `< minChainLength`) (Priority 2):**
   - `409 CHAIN_ALREADY_SUBMITTED` (`src/domain/errors/domain-errors.ts:152-161`) when a learner re-submits the identical path or the exact reverse path in the same round is untested in BDD.
   - `422 CHAIN_TOPOLOGY_INVALID` for a chain shorter than the pack's `minChainLength` (e.g., 2 cells when `diabe-teach` requires 4) already has a step definition in `tests/integration/step-definitions/chain-submission.steps.ts:168-195` (`When("participant {string} submits a chain that is too short")`), which passes the OpenAPI `minItems: 2` request schema check and exercises domain validation, but is never called in `classroom-session-journey.feature`.

5. **Post-Leave Write Refusals (`403 PARTICIPANT_HAS_LEFT`) Across Voting, Assessments, and Survey (Priority 2):**
   - `classroom-session-journey.feature:220-239` verifies that a participant who calls `POST /api/v1/sessions/:sessionId/leave` gets `403 PARTICIPANT_HAS_LEFT` when submitting a chain, and `200` when reading session state.
   - However, OpenAPI (`docs/api/openapi.yaml:819-826, 1359-1371`) guarantees that *every* participant write route (`adjudicateConceptChain`, `submitAssessmentAttempt`, `submitPerceptionSurvey`) also refuses a learner who left with `403 PARTICIPANT_HAS_LEFT` while read routes (`listRoundChains`, `getRoundStandings`, `getGameSessionState`) continue to work. Extending the leave scenario (or adding assertions) to cover peer voting and assessment/survey submission after leaving verifies this invariant end-to-end.

6. **Phase Transition & Session Lifecycle Refusals (`409 INVALID_PHASE_TRANSITION`, `404 PACK_NOT_FOUND` on Create Session, `400` Invalid Path/Body Params) (Priority 2):**
   - `409 INVALID_PHASE_TRANSITION` when an instructor attempts to skip phases via `{ action: "jump", targetPhase: "completed" }` on `POST /api/v1/sessions/:sessionId/phase` (step `When("the instructor jumps to phase {string}")` already exists at `phase-transition.steps.ts:47-61`!).
   - `404 PACK_NOT_FOUND` when creating a session (`POST /api/v1/sessions`) with a non-existent `packId`.
   - `400 INVALID_REQUEST_BODY` when calling `GET /api/v1/sessions/:sessionId/rounds/3/chains` (invalid `:roundNumber` path parameter) or `POST /api/v1/sessions/:sessionId/phase/extend` with `{ seconds: 0 }` or `{ seconds: 601 }`.

7. **Assessment & Survey Semantic / Schema Validation (`422 ASSESSMENT_INCOMPLETE`, `422 SURVEY_COMMENTS_TOO_LONG`, `400 INVALID_REQUEST_BODY`) (Priority 3):**
   - `assessment-journey.feature` only tests `409` errors (`ASSESSMENT_ALREADY_SUBMITTED` and `PHASE_CLOSED_FOR_SUBMISSIONS`). It never tests `422 ASSESSMENT_INCOMPLETE` (submitting fewer than 10 answers for `diabe-teach`) or `400 INVALID_REQUEST_BODY` (submitting an answer choice outside `0..3 | "I_DONT_KNOW"`).
   - `survey-journey.feature` only tests `409` errors (`SURVEY_ALREADY_SUBMITTED` and `PHASE_CLOSED_FOR_SUBMISSIONS`). It never tests `400 INVALID_REQUEST_BODY` (Likert rating `6` or `0` naming `responses.<itemId>`) or `422 SURVEY_COMMENTS_TOO_LONG` (>1000 words).

8. **HTTP Middleware Order & `413 PAYLOAD_TOO_LARGE` / Malformed JSON Over `netlify dev` (Priority 3):**
   - `tests/functions/bad-request-body.test.ts` thoroughly tests `413 PAYLOAD_TOO_LARGE` (>256 KB) and malformed JSON in-process, but BDD never sends a >256 KB payload or malformed JSON string through `supertest` → `netlify dev` → `wrapLambdaHandler` (`request.text()`, `src/adapters/inbound/http/lambda-to-v2-wrapper.ts:110-112`) → `createApiHandler`. Having even one smoke scenario in BDD verifying that `netlify dev` passes a >256 KB body to the v2 function and returns `413 PAYLOAD_TOO_LARGE` (and `401` first when unauthenticated) validates the serverless runtime wrapper under real HTTP.

### 3.2 Errors Best Left to Vitest Handler Tests (`tests/functions/*.test.ts`)

Per `.scratch/session-phase-deadlines/wiki/decision-test-seam-handlers-plus-clock.md:10-13`, the BDD Cucumber suite communicates over HTTP with a separate `netlify dev` OS process, so `TestWorld.clock` (`FakeClock`) cannot control the server's wall clock. Consequently, the following edge cases are **best kept in `tests/functions/*.test.ts`** and should **not** be duplicated in BDD:

1. **Exact clock-boundary & long-duration timer tests:**
   - The 5-second Chain-Mapping submission grace period boundary (`phaseEndsAt + 5.000s` accepted vs. `phaseEndsAt + 5.001s` rejected with `409 PHASE_CLOSED_FOR_SUBMISSIONS` — tested in `tests/functions/session-phase-deadline.test.ts:231-272`). Note: `classroom-session-journey.feature:177-192` already has one real-time sleep scenario (`1s + 5s grace + 0.5s = 6.5s` wait in `phase-transition.steps.ts:163-177`); adding more real-clock sleeps to BDD would slow the suite and risk flakiness.
   - The 15-minute `AccountTemporarilyLockedError` lock duration and automatic unlock at `15m 00s` (`tests/functions/instructor-accounts.test.ts:322-355`). *(Note: triggering the lock on the 5th wrong password requires no wait and can be tested in BDD, whereas waiting 15 minutes for unlock must stay in Vitest.)*
   - The 12-hour Account Token expiry (`tests/functions/instructor-accounts.test.ts:425-435`, `tests/functions/create-session.test.ts:285-290, 345-387`).
2. **Deterministic optimistic-concurrency write-conflict races (`409 CONCURRENT_UPDATE_CONFLICT`):**
   - Testing 1-conflict retry recovery and 3-attempt exhaustion (`409 CONCURRENT_UPDATE_CONFLICT`) requires deterministic interception between `findById` and `update` via `RaceBeforeFirstSaveSessionRepository` and `AlwaysConflictingSessionRepository` (`tests/functions/session-write-conflict.test.ts:475-515`, `tests/functions/session-board.test.ts:370-398`). Over live HTTP against MongoDB, racing requests are non-deterministic.
3. **Simulated repository crashes (`500 INTERNAL_ERROR`):**
   - Verifying that an unhandled exception in a repository returns a generic `500 INTERNAL_ERROR` without leaking stack traces requires injecting a throwing repository double (`tests/functions/bad-request-body.test.ts:378-444`, `tests/functions/request-summary-log.test.ts:121-147`).
4. **Exhaustive combinatorial schema property matrix:**
   - `tests/functions/request-body-schema.test.ts:438-484` dynamically iterates over every `required` property and every typed property of all 12 write operations in `openapi.yaml`. Running ~100 schema permutations over HTTP in Cucumber would add unnecessary runtime when 2–3 representative schema checks in BDD suffice to prove the middleware is wired in `netlify dev`.
5. **Custom `API_KEY` header enforcement (`x-api-key`):**
   - In `netlify dev`, `API_KEY` is fixed per server process (`tests/integration/support/http-client.ts:7`), whereas handler tests (`tests/functions/list-packs.test.ts:85-115`, `tests/functions/get-pack-by-id-comprehensive.test.ts:161-186`) can toggle `requireApiKey: true/false` per test.

## 4. Actionable Recommendations for New BDD Scenarios

If you decide to expand BDD non-happy-path coverage, the **13 concise scenarios** below (grouped by existing `.feature` file) close every high-value gap identified in Section 3.1 without introducing any wall-clock sleeps.

### 4.1 `tests/integration/features/classroom-session-journey.feature` (+5 scenarios)

1. **`Scenario: Peer voting, instructor final ruling lock, and adjudication error handling`** (`@adjudication @error-handling`)
   - Exercises the currently untested `POST /api/v1/sessions/:sessionId/rounds/:roundNumber/chains/:chainId/adjudicate` and `GET .../standings` routes end-to-end:
     - Alice submits a chain in `round-1:chain-mapping`; instructor advances to `round-1:peer-adjudication`.
     - Bob casts `peer-approve` (`200`).
     - Bob attempts `instructor-approve` → refused with `403 FORBIDDEN_ROLE`.
     - Instructor attempts to adjudicate a non-existent chain ID → refused with `404 CHAIN_NOT_FOUND` (verifying `:chainId` survives `netlify dev`'s 404 `.html` retry).
     - Instructor finalizes ruling with `instructor-approve` and score `8` (`200`, `chain.verdict.isLocked === true`).
     - Bob attempts another peer vote (or instructor attempts to re-rule) on the locked chain → refused with `409 ADJUDICATION_LOCKED_BY_INSTRUCTOR`.
     - Instructor and Alice retrieve standings for round 1 (`200`, Alice ranked 1).
   - *Reuses existing unused steps in `chain-submission.steps.ts:197-277` plus 2 small steps for peer-attempting-instructor-ruling and missing chain ID.*

2. **`Scenario: Duplicate, reversed, and too-short concept chains are rejected`** (`@chain-submission @validation`)
   - In `round-1:chain-mapping`:
     - Alice submits a 2-cell chain (`When participant "Alice" submits a chain that is too short`, already implemented at `chain-submission.steps.ts:168-195`) → `422 CHAIN_TOPOLOGY_INVALID`.
     - Alice submits a valid 4-cell chain → `201`.
