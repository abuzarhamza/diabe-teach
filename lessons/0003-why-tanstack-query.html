The problem: server state is not like useState

In Namaste React you kept everything in useState: the search text and the restaurant list alike. The TanStack Query team splits these into two kinds. Client state belongs to the browser: the text in a field, which tab is open. Server state is different. Their overview lists four properties (TanStack Query, Overview):

  1. It “is persisted remotely in a location you may not control or own”.
  2. It “requires asynchronous APIs for fetching and updating”.
  3. It “implies shared ownership and can be changed by other people without your knowledge”.
  4. It “can potentially become ‘out of date’ in your applications if you're not careful”.

Now think of our game. A Game Session lives in MongoDB. The instructor and 25 learners change it at the same time. Every learner's screen must follow the phase within about 2 seconds. That is property 3 and 4 at full strength. ADR-0008 therefore says: session state is polled with useQuery({ …, refetchInterval: 2000 }), and useEffect is banned (Layer Rules 3 and 4).

Same job, two ways

TeacherRoute must confirm the teacher with GET /api/v1/accounts/me. First is how the course would write it. Second is the real code, written in TeacherRoute.tsx when this lesson was made; since commit 5efbd2c it lives in useCurrentAccount in web/src/features/accounts/account-hooks.ts (lesson 0004).

Course style: useEffect + useState (not allowed here)

const [data, setData] = useState(null);
const [error, setError] = useState(null);
const [loading, setLoading] = useState(false);

useEffect(() => {
  if (!account) return;
  let cancelled = false;              // 1. ignore a late answer after the teacher changes
  setLoading(true);
  async function load(attempt = 0) {
    try {
      const me = await getCurrentAccount();
      if (!cancelled) setData(me);
    } catch (e) {
      if (e.status !== 401 && attempt < 3) return load(attempt + 1);  // 2. retry by hand
      if (!cancelled) setError(e);
    } finally {
      if (!cancelled) setLoading(false);
    }
  }
  load();
  return () => { cancelled = true; };  // 3. cleanup
}, [account?.accountId]);              // 4. get the dependency list right
// 5. no cache: a second component that needs /me sends a second request
// 6. polling every 2 s would need setInterval + clearInterval on top

This app: useQuery

const confirmation = useQuery<InstructorAccountView, ApiHttpError>({
  queryKey: ["accounts", "me", account?.accountId],   // cache entry; a new teacher → a new key
  queryFn: getCurrentAccount,                          // from web/src/api/ — the only fetch layer
  enabled: account !== null,                           // do not ask while signed out
  retry: (failureCount, error) => error.status !== 401 && failureCount < MAX_RETRIES,
});
// confirmation.data · confirmation.error · confirmation.isPending — all derived, no setState

Every numbered comment in the first version is something you could get wrong. In the second, the library owns it: late answers, retries, cleanup, the key, the cache and the request de-duplication. Polling is one option: refetchInterval: 2000 (useQuery reference).

The three pieces this app uses

QueryClient + QueryClientProvidermain.tsx · App.tsx

The QueryClient holds the cache. main.tsx creates one for the browser. App.tsx provides it to every screen. Each test makes a fresh client with retry: false (web/tests/support/render-app.tsx), so tests do not share a cache and fail fast.

useQuery: readTeacherRoute.tsx → getCurrentAccount

For data you read from the server. You give a queryKey (the cache address, unique to the data, Query Keys) and a queryFn from api/. You get data, error and isPending. Planned: the Session Shell polls the Game Session with refetchInterval: 2000.

useMutation: writeLoginPage.tsx → signIn, signUp

For actions that change something, started by an event handler: signIn.mutate(credentials). isPending disables the buttons. error feeds loginErrorView. onSuccess navigates (Mutations).

Note: the Account Token is not in TanStack Query. It is not server state: the browser owns it in localStorage. So the app reads it with useSyncExternalStore (useSignedInAccount). The rule of thumb:

Server state, readthe signed-in account (/me), packs, Game SessionuseQuery

Does it replace Redux? For most apps, the TanStack team says the client state left over after moving async code into the library “is usually very tiny” (Does this replace client state?). That is why this app has no Redux store.
